`TerminalManager` is the owner of live PTYs. Each attached session has a runtime
containing:

- A `node-pty` child.
- A headless xterm instance.
- An optional Codex/Claude screen detector.
- A short debounce timer for screen scans.
- A bounded retry timer for Codex provider-session discovery.
- App-exit and current-session metadata.

## Creation

Starting a terminal:

1. Resolves its project and connection.
2. Checks whether tmux is available.
3. Validates or generates a tmux-safe unique name.
4. Persists the new `idle` session before process launch.
5. Builds versioned `@panepilot_*` tmux metadata from the persisted session.
6. Spawns its local or remote PTY.

The pane sets its tmux metadata before executing the selected profile. The metadata
contains a stable terminal UUID, originating project ID, canonical project folder,
profile, session kind, creation time, safety indicator, and any known Action, provider,
or LaTeX chat identity. The pane is targeted explicitly through `TMUX_PANE`, which
prevents a nested tmux client from accidentally tagging the caller's session.

A failed process spawn can therefore leave a persisted session that records the launch
attempt and can transition to an error.

For a new Codex session, the runtime also polls provider archives for the unclaimed
Codex session ID whose working directory and start time match the terminal. A
`terminal:metadata` event refreshes the renderer after a successful link.

## Local commands

For a tmux-backed local session, PanePilot creates:

```text
tmux new-session -s <name> -c <project-folder> <launch-command>
```

Reattachment uses an exact session target:

```text
tmux attach-session -t =<name>
```

Without tmux, shell profiles spawn the configured shell with `-l`; other profiles use
the configured shell with `-lc`.

## Remote commands

Remote sessions spawn local `ssh -tt`. The remote command first changes to the project
folder, then creates or attaches to tmux when available. Agent and Action commands are
wrapped in the remote user's interactive login shell so normal remote PATH setup is
applied.

Remote tmux discovery, existence checks, and rename operations run separately with
batch-mode SSH and short timeouts.

Interactive SSH clients use server keepalives. If a client exits unexpectedly,
PanePilot preserves terminal lifecycle state, verifies the exact managed tmux UUID,
and reconnects with bounded backoff. Electron resume proactively replaces possibly
stale SSH clients.

## Remote discovery and reconciliation

PanePilot periodically asks the selected SSH user's default tmux server for all
sessions and their `@panepilot_*` user options. No remote daemon or PanePilot service is
installed.

The canonical remote project folder is the portable project match across laptops;
local project UUIDs may differ. The stable terminal UUID is then used to upsert a local
SQLite row:

- A tagged remote session missing locally is imported.
- A known session refreshes its name, profile, provider link, and safety indicator.
- A legacy untagged session with the exact name of a known local terminal is adopted
  by adding metadata.
- A metadata-managed local row is marked completed when a successful remote scan
  proves that its tmux session no longer exists.
- An unreachable host leaves cached local state unchanged.
- Codex pane-title fields refresh current `run-state` and `task-progress` without
  consuming a per-device event stream.

LaTeX chat scope, mode, and portable section source/title information are included so
an imported chat can be reconciled with the receiving laptop's section identities.
Discovery displays matching terminals but does not immediately attach every tmux
client; attachment occurs when the user selects a terminal.

## Action runs

An Action definition lives independently of its latest terminal session. Running it:

1. Requires tmux on the project connection and rejects a second invocation while its
   current command is still active.
2. Deletes the completed prior session and saved output.
3. Creates and links a new session with internal profile `custom` and kind `action`.
4. Runs the definition through the user's shell from the project folder.
5. Leaves xterm input connected until the command exits.

The tmux server removes the ephemeral session when the command exits. PanePilot then
marks the run completed and retains its bounded output until rerun or deletion.

## Project Q&A

The partial SQLite uniqueness constraint permits one `project-qna` session per
project. It requires tmux and uses the normal Codex launch, provider-ID discovery,
lifecycle tracking, persistence, and exact resume behavior, but renderer workspaces
expose it through the top-level Project Q&A tab instead of ordinary terminal
navigation.

## Exact Codex resume

tmux persistence and provider resume solve different problems:

- Reattachment reconnects xterm to a Codex process that is still running in tmux.
- Provider resume starts a new Codex process for a stopped or errored terminal with
  `codex resume <provider-session-id>`.

Resume is limited to linked Codex terminals that are not archived. PanePilot uses the
same project folder, connection, dangerous-mode setting, and terminal identity. It
attaches instead if the named tmux session still exists.

Provider session discovery reads `session_meta` records independently of lifecycle
hooks. On startup PanePilot makes a best-effort pass over unlinked Codex terminals,
using the local indexer or the remote indexer associated with the terminal's original
connection.

Once a Codex or Claude provider ID is discovered, PanePilot writes it to SQLite and
the live tmux user options. Another laptop can therefore import both the terminal and
its exact resumable provider identity.

## Output and rendering

Each PTY data chunk is handled in three independent paths:

1. Append the raw bytes to the capped SQLite output.
2. Send a `terminal:data` event to the active BrowserWindow.
3. Write the data to headless xterm and schedule a screen scan.

The renderer creates its own xterm with a 5,000-line scrollback and a fit addon. It
subscribes to live data, attaches the session, replays saved output, then enables
`onData` forwarding and focuses the terminal.

Replaying while input forwarding is disabled is an important invariant. xterm can emit
protocol replies while interpreting old output; forwarding those replies would write
numeric garbage into the live PTY.

## Reattachment

If a tmux session has no current runtime, PanePilot launches an attach PTY. A remote
SSH client exit changes only transport state to Reconnecting or Offline. PanePilot
marks the terminal completed only after a successful scan proves that the exact
metadata-tagged tmux session no longer exists.

PanePilot-managed Codex launches mirror `activity`, `run-state`, and `task-progress`
into the tmux pane title. Because tmux owns that snapshot, every laptop reads the same
current value without a remote spool. Working/Thinking restores `running`,
action-required restores `needs-input`, and Ready after Working becomes
`response-ready`.

A detached PTY backend cannot be recovered. PanePilot marks it completed with an
activity explaining why.

## Exit and shutdown

An unexpected local process exit maps code zero to `completed` and any non-zero code
to `error`. A remote tmux attachment exit begins reconnection instead. A
user-requested stop marks the session completed immediately and then tears down its
backend.

During application exit, attached PTYs and screen instances are disposed without
changing stored terminal state. tmux sessions continue to run; plain PTY processes end.

## Current activity detector

The headless xterm exposes the rendered viewport, not the raw output stream. After a
120 ms debounce, the detector searches visible text for `esc to interrupt`. Seeing it
arms the turn and sets Working; seeing it disappear after being armed sets Needs
attention.

Raw terminal output is never modified to carry lifecycle metadata. The remote Codex
snapshot is queried from the tmux pane title separately.
