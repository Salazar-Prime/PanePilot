Agent state describes what PanePilot believes the current terminal needs. The shared
model includes seven states:

| Internal state | UI label | Meaning in the current implementation |
| --- | --- | --- |
| `idle` | Ready | The session is open and not currently detected as working |
| `running` | Working | A Codex or Claude working marker is visible |
| `needs-input` | Needs input | Codex reports an action-required title or PanePilot detects a live queued question |
| `response-ready` | Response ready | A remote Codex pane returns to Ready after Working |
| `needs-attention` | Needs attention | A previously visible working marker disappeared |
| `completed` | Stopped | The terminal process or tmux session ended normally or was stopped |
| `error` | Error | The terminal exited with a non-zero code |

## Detection today

Local and legacy agent sessions receive a screen detector. The detector examines the
current rendered terminal viewport after output settles:

```text
"esc to interrupt" appears
        │
        ▼
     running
        │
        │ marker later disappears
        ▼
 needs-attention
        │
        │ terminal is opened or reselected
        ▼
       idle
```

Shell terminals and Action runs are excluded, so ordinary command output cannot create
an agent Working state. Codex terminals, Quick Codex chats, and LaTeX writing chats
participate in normal lifecycle and attention counts.

Remote PanePilot-managed Codex sessions additionally mirror `activity`, `run-state`,
and `task-progress` into their tmux pane title. Every laptop reads the same current
snapshot, so no remote event spool is required. `task-progress` describes the latest
Codex plan update; `run-state` remains the liveness signal.

Codex may show a **Queued follow-up inputs** footer while its title still says Working.
PanePilot requires the complete live footer—a heading, positive question count, and
answer shortcut—within the last eight rendered screen rows before marking the session
**Needs input**, so old scrollback or ordinary output does not trigger it. Attached
screens update directly. Each discovery pass checks only a bounded, rotating set of
detached working Codex panes through read-only tmux captures, including over SSH. A
successful capture without the footer clears this queued-question alert back to the
pane-title state. Failed or skipped captures cannot clear it, and stronger explicit
approval-required evidence remains sticky. Submitting terminal input alone does not
clear the alert.

## Where status appears

- A state dot on every project and terminal row.
- An animated Working indication for `running`.
- An attention badge on `needs-input`, `needs-attention`, or `response-ready`.
- Aggregate Working and attention counts in the bottom status bar.
- State-change entries in the project Activity tab.

## Project aggregation

The project state is the highest-priority state among its visible sessions:

```text
needs-input
needs-attention
running
response-ready
idle
error
completed
```

This ordering prioritizes actionable live work over passive or ended sessions.

## Important limitation

The pane-title snapshot is intentionally current-state-only and does not retain
intermediate transitions while every PanePilot client is offline. Do not interpret
task progress alone as proof that Codex is actively generating.
